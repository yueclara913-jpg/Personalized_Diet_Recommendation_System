# 每日饮食记录与营养摄入统计

本模块建立“健康档案 → 每日目标 → 饮食快照 → 每餐/每日汇总 → 营养缺口”的 Python 服务基础，不提供疾病诊断或治疗建议。项目尚无普通用户认证和对象级授权，因此没有个人饮食记录 HTTP CRUD 或浏览器页面。

## 数据与来源

每条记录保存 profile ID、日期、餐次、克数、来源引用及能量/蛋白质/脂肪/碳水的每 100 g 不可变快照和 SHA-256。有能量值时必须同时记录 `energy_definition`，该口径也参与快照哈希；本阶段不支持糖，因此不会混合总糖、添加糖等定义。当前仅接受 `manual_unverified` 和 `external_unverified`，不能声称来自正式 approved 食品；旧 CSV、USDA 暂存和人工候选审核均不会自动成为可信来源。缺失营养项存为 NULL，真实零保存为 0。份量只执行 `每100g数值 × amount_g / 100`，采用 Decimal 和 ROUND_HALF_UP 两位显示，不推断可食部、密度、烹调损耗或未知单位，也不以 4-4-9 改写来源能量。

## 独立数据库

饮食库 application_id 为 `0x44494554`、user_version 为 1，严格校验 schema，初始化拒绝覆盖或符号链接。写入使用参数 SQL、显式事务、失败回滚和 `updated_at_utc` 乐观并发。删除采用 `revoked` 软撤销，营养来源快照不可通过更新接口改变。饮食库与健康档案、管理员认证、营养审核和 USDA 暂存库物理隔离。

跨库无法建立天然外键或单一原子事务。每个仓储操作会先在健康档案库显式确认 profile ID 存在；当前健康档案模块没有删除功能，从而降低检查后失效风险。未来增加档案删除时必须设计跨库停用与补偿流程，不能宣称现有检查是跨库事务。

## 汇总与完整性

每餐和每日分别输出记录数、每项已知小计、完整总量、未知记录数、状态和单位。无记录为 `no_records`，全部未知为 `unknown`，部分未知为 `partial`，全部已知（包括真实零）为 `complete`。partial 的已知小计仅供展示，完整 total 保持 NULL，防止伪精确统计。每日结果还提供餐次数、各餐明细、未验证来源数量和可信度提示。

`analyze_daily_nutrition()` 校验档案及记录归属，直接复用 PR #11 的 `calculate_daily_targets()` 和 `calculate_nutrition_gaps()`。PR #11 抛出的 `ManualReviewRequired` 会原样阻断分析。只有状态 complete 的摄入总量传给缺口函数；partial、unknown 和 no_records 均传入 None，因此缺口保持未知。

下一阶段在普通用户认证、对象级授权、隐私策略和正式食品发布链完成后，才适合增加记录页面及将完整摄入统计用于推荐排序。
